Ask the Data: a guarded LLM assistant

A question-answering assistant over the Indonesia Realtime Monitor data, in plain Indonesian, running a 3B model locally with Ollama on a 4 GB laptop GPU. The model never writes SQL and never supplies the numbers: it picks from ten predefined tools, the system runs parameterized queries and computes the facts, and the model only phrases the answer. The same local model classifies and geotags the news feeding the platform.

Tools, not text-to-SQL

Ten predefined tools (earthquakes, hotspots, air quality, food prices, news, pipeline health, weather forecast, internet outages, operator speed & traffic, cell distribution) with a rule-based router as a safety net when the model picks badly.

Facts computed by code

Every answer is built on deterministic fact sentences shown beside it, added after the small model turned "993 hotspots" into "the highest value is 993".

Guardrails from real failures

Parameters must appear in the question, added after the model copied "Jakarta" from a prompt example. Map coordinates always come from a gazetteer, never from the model.

App Tagging Stream: Kafka to ClickHouse

Tags network hostname events to applications and categories as they stream through Apache Kafka (4.1, KRaft) into ClickHouse. The hostname dictionary is built from v2fly/domain-list-community, pinned to an upstream commit, versioned with a diff, and re-synced every six hours; the consumer picks up a new version without a restart. A small supplement covers Indonesian apps missing upstream. Events are synthetic: no subscriber data is used.

Measured, not claimed

On 82,200 events through the running stack: precision 1.0 and recall 96.6%, the same as the offline evaluation. Third-party sites using a brand name are never tagged as the brand, and phishing lookalikes go to a review queue. A first evaluation that scored 100% against its own patterns was replaced with held-out cases.

At-least-once, proven

Offsets are committed only after the ClickHouse insert succeeds. A test fails an insert in the middle of the stream and checks that no event is lost; every event carries an id, so duplicates are measurable (none in the run).

Found by testing

Brand top-level domains (.youtube) that were never checked, appletree.com tagged as Apple, an empty-batch commit failing in Kafka, a consumer that stopped before the group rebalance, and a package path that only broke inside Docker.

Data Governance Dashboard & BigQuery FinOps Toolkit

One governance dashboard with two sources. Seven modules run on a synthetic warehouse (3,494 objects across 18 projects, 1.85 PB) and answer the questions a data platform lead asks every month: where storage and compute money goes, which tables nobody reads, who runs the expensive queries, which loads are broken, what breaks downstream if a table changes, and what the data means, plus an app-store catalogue dashboard. The live report applies the same questions to a real BigQuery project, on two small sample warehouses (public e-commerce data and a telco warehouse generated in SQL), through my open-source Python toolkit, which reads INFORMATION_SCHEMA and the Tables API: cost by user, pipeline and query pattern, partition, cluster, SELECT * and unused-table recommendations with evidence, lineage, a data dictionary, data quality checks and LLM-drafted descriptions applied only after review. A re-implementation of a governance suite I built at work, with no employer code or data; the interface uses the open-source CoreUI admin style.

Network KPI Monitor: 2G, 4G, 5G, WPC, site map, assurance and public Internet data

One OSS-style dashboard for a synthetic two-vendor network (Ericsson/EID and ZTE) laid over the public map of Kalimantan: 7 branches, 2,137 generated sites and 30,435 cells on GSM, DCS, L9, L18, L21, L23, NR21 and NR23, with a fiber and microwave transmission topology. The performance views show site counts per branch and band, daily payload and availability, a site map, the daily worst-performing-cell (WPC) list and 2G/4G/5G KPIs from vendor to site and cell. The assurance views show what happens when the network breaks: a week of alarms correlated to root causes, sleeping cells found from KPIs, customer SLA impact and capacity-aware provisioning. Alarm names follow public references; all events are generated by code. A third group of views uses real public data from Cloudflare Radar (CC BY-NC 4.0), refreshed by GitHub Actions: Internet outages and traffic anomalies in Indonesia, hourly traffic per operator ASN with a drop detector, speed tests per operator, and BGP routing, RPKI, hijack and leak events; plus cell distribution per regency from OpenCelliD (CC BY-SA 4.0) compared with telecom towers mapped in OpenStreetMap (ODbL), with both sources' blind spots flagged. Modeled on the multi-vendor OSS work I did for mobile operators for about a decade.

Counters, one formula for both vendors

Ericsson and ZTE counters are mapped to one schema, and every KPI is Σ numerator ÷ Σ denominator at the level shown, from cell to branch. Worst lists require a minimum denominator, so a cell with three attempts and one failure does not top the list.

Alarm storm to root cause

21,881 alarms become 161 network incidents by walking the transmission tree and the order of events. On deliberately messy data (lost alarms, clock skew) 90% of network faults get the correct root cause; the ambiguous case, two nested cuts minutes apart, is documented as a known limit.

What alarms miss

All 30 cells that stop carrying traffic without raising any alarm are found from KPIs alone. Customer downtime is measured from the counters and traced to its incident: every Gold service hit in the week used up its monthly budget, an argument for path redundancy.
